# ssot-reuse：一处定义，处处引用

## 何时用
准备写 const / def / class / interface / 配置项，或复制粘贴一段代码时。

## 硬规则
- MUST 新增定义前搜索代码库，检查已有定义的语义和契约，再决定是否复用。
- NEVER 同一事实存在于两处（常量、枚举值、URL、schema、业务规则）；第二处必须引用第一处。
- MUST 相似代码再次出现时先比较职责与变化原因；同一规则复用已有定义，职责一致且会同步变化时才抽象。
- MUST 新方法先问"接口还是一次性用法"：会被两处以上调用的定义为接口（明确输入、输出、错误），不写调用方专用逻辑。
- NEVER 仅为减少相似行数，把独立变化的逻辑塞进参数或分支。
- MUST 抽象后删除原重复，不留旧版本；新结构里值得完全理解的部分指出位置。

## 审问清单
1. 这个名字 / 值 / 结构已经有了吗？搜过哪些关键词？
2. 它属于哪一层？放进那层的现有模块还是新建？
3. 两个相似函数会因同一原因改变吗？差异适合参数化，还是应独立维护？
4. 这是接口（稳定契约）还是实现细节（可随时改）？
5. 删掉重复后，谁还依赖旧位置？

## 反模式
- 错误：`MAX_RETRY = 3` 在三个文件各写一遍。→ 正确：`config.MAX_RETRY` 一处定义，其余引用。
- 错误：`fetchUserById`、`fetchUserByEmail` 各自拼查询、各自处理错误。→ 正确：`fetchUser(where)` 一个接口，调用方传条件。
- 错误：接口返回类型在前端、后端、文档各手写一份。→ 正确：schema 单一来源（OpenAPI / zod / pydantic），其余生成。
- 错误：两个校验函数结构相似，合成带业务类型开关的通用函数。→ 正确：规则与修改原因不同就分别维护，只复用确实共用的规则。

## 输出要求
新增定义时说明：搜了什么、为何无可复用项、放在哪一层。抽象时列出被替换的重复位置。
