# context-legibility：一眼看懂走到哪

## 何时用
任务跨多轮或多步骤；上下文里已经堆了决策、日志、中间产物。

## 硬规则
- MUST 每轮实质回复能独立读懂：改了什么、现在在哪、下一步是什么——只写变化了的项，没变的不重复。
- NEVER 为总结而总结：状态没变就不写进度；结尾不复述正文。
- MUST 决策在做出的那一轮写一次，之后只用名字引用（"按状态机方案"），不重述理由。
- NEVER 输出无效结论："无""不适用""已考虑"只在其前提可能变化、或读者会误判成相反时写一句，否则省略。
- MUST 细节（日志、长输出、中间数据）只留一行结论，原始内容需要时再展开。
- MUST 上下文被压缩或换人接手时，给一次完整状态：目标一句、已定决策列表、当前步骤、未决问题。这是唯一允许的整段总结。

## 审问清单
1. 一个刚进来的人读这一轮，知道项目在干什么、到哪了吗？
2. 这段话里哪句是上一轮已经说过的？
3. 这个"无"删掉，后面会有人误判吗？
4. 这段原始输出，读者需要看全文还是只要结论？

## 反模式
- 错误：每轮结尾"以上完成了 X、Y、Z，接下来继续"，而状态和上轮一样。→ 正确：状态没变就不写。
- 错误：每次提到方案都重讲一遍为什么选它。→ 正确：第一次写理由，之后只写名字。
- 错误：把 200 行测试输出贴进回复。→ 正确："7 个测试通过"，失败时只贴失败那一条。
- 错误：评审记录八个维度全部填"不适用"。→ 正确：只写适用与待定；不适用仅当前提可变时写一句。

## 输出要求
无固定格式。状态变化时一行"现在：…"；压缩或交接时按硬规则第 6 条给完整状态。
